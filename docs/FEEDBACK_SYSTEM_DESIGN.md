# Feedback System Design & Integration Plan (Supabase Edition)

## 1. Objective

Implement a user feedback submission feature that includes frontend UI and a complete backend endpoint saving to Supabase (PostgreSQL). The system must be environment-agnostic so it can work with a development Supabase project now, and seamlessly switch to the production Supabase project later via `.env` variables without code changes.

## 2. Database Strategy (Supabase / PostgreSQL)

- Since Supabase is built on PostgreSQL, it is a relational database. We **must** pre-create the table and define the schema before inserting data.
- Table Name: `feedbacks`.
- Environment Variables required in `.env`:
    - `DATABASE_URL` (The PostgreSQL connection string from Supabase settings)
    - OR `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` (if using Supabase REST APIs via a Rust client).
- **SQL Migration:** The AI assistant must use the following SQL to create the table in Supabase:

```sql
CREATE TABLE feedbacks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  topic VARCHAR(100) NOT NULL,
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now(),
  user_id UUID -- Nullable. Use UUID to match Supabase's auth.users id
);
```

## 3. Data Structure (DTOs & Schema)

### 3.1. Feedback Model (Rust Struct for Database)

The database model mapped in Rust should contain:

id: UUID (Auto-generated by PostgreSQL).

topic: String (A short categorize/topic field. Used to store structured data that will fuel an autocomplete/suggestion system in future dashboards).

content: String (Free-text feedback).

created_at: DateTime (Auto-generated timestamp of submission).

user_id: UUID (Optional, extracted from JWT token if the user is logged in).

### 3.2. Request DTO (From Frontend to Backend)

Validation Rules:

topic: Required. Max length: 100 characters.

content: Required. Max length: 5000 characters.

```json
{
    "topic": "Feature Request",
    "content": "I would love to see a dark mode option in the settings. Here are my thoughts..."
}
```

### 3.3. Response DTO (From Backend to Frontend)

```json
{
    "status": "success",
    "message": "Thank you for your feedback!",
    "data": {
        "feedback_id": "123e4567-e89b-12d3-a456-426614174000"
    }
}
```

## 4. Backend Implementation Requirements

Endpoint: POST /api/feedback

Controller/Service:

Receive the Request DTO.

Validate the string lengths (content <= 5000, topic <= 100). Return 400 Bad Request if invalid.

Map Request DTO to the Rust database struct.

Insert the record into the feedbacks table using the configured database driver (e.g., SQLx, Diesel, or Supabase crate).

Middleware: Apply the existing User JWT extractor if we want to track who sent the feedback (optional, but recommended). If the user is authenticated, attach their UUID to the user_id field.

## 5. Frontend Implementation Requirements

HomePage Element: Add a highly visible "Feedback" button (e.g., a floating action button or a clear button in the navigation/footer).

Feedback Form (Modal or Page):

Input 1 (Topic): A text input field for the "Topic/Subject" (with a note that this helps categorize).

Input 2 (Content): A `` for free text. Must include a character counter showing current_length / 5000.

Submit Button: Handles the API call and shows a success toast/message based on the Response DTO.
